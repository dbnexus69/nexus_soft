## Frontend architecture

`src/App.tsx` nests one Context provider per domain (Auth → Users → Clients → Sales → Commissions → Data); `PermissionsProvider` sits inside `ProtectedRoute`. Route guards: `ProtectedRoute`, `AdminRoute`, `SuperadminRoute` (`/companies`). Most cross-cutting state lives in `src/context/*`. The internal-management catalogs (airlines, suppliers, payment methods…) live only in `DataContext` (`data.config`); the settings screen and the sales wizard read the same copy, so there must not be a second one.

`api/client.ts` is the single axios instance (`VITE_API_URL`, Bearer token from `localStorage['nexus_token']`, clears it on 401); `src/api/*.ts` are thin per-resource wrappers. `api/fetchAll.ts` is the one place that pages through a whole collection when a full list is genuinely needed — never a huge `perPage`, the server caps it at 100 and it truncates silently. `src/utils/*Cache.ts` are localStorage caches with TTLs keyed by empresa and user, invalidated on mutation and on logout. `PermissionsContext` mirrors the backend permission shape — keep both in sync. Agency name and logo come from the tenant (`GET /branding`); brand colors apply only to the voucher, not the UI. `components/` is organized by domain; `sales/` splits into `forms/ steps/ wizard/ detail/ credit/` for the multi-step sale flow and its ~15 product types.

**Quotes reuse the sale forms, never a parallel set** (spec 007). `pages/Quotes.tsx` renders the same `Step2Products`/`ProductFormsModal`/`useSaleCalculations`/`WizardFormData` (from `wizardData.ts`) the real sale wizard uses, with a plain `WizardFormData` draft and no client picker (a quote has no client until it's converted). Each `forms/*.tsx` component takes an optional `cotizando?: boolean` prop (default `false` — `NewSaleWizard.tsx` never passes it, so the real sale flow can't be affected): when `true`, it hides whatever depends on a sale that doesn't exist yet — passenger/guest/titular identity, ticket/reservation/confirmation numbers, seats — wrapped in `{!cotizando && (...)}` right where that field already lived, never moved to a separate component. Everything that describes the service itself (dates, destination, type, counts, cost, ganancia) stays, with the same design. An earlier attempt built quote-only mini forms with a different look; it was reverted because the product only wanted the *fields* trimmed, not a different design — don't repeat that. `forms/PlanForm.tsx` keeps hotel data and flight/transport data in their own sections ("Hotel del Plan" vs "Vuelo del Plan"/"Transporte Terrestre del Plan") — don't remix them back together when touching that form. The read-only view of a closed quote (`Quotes.tsx`'s `readOnlyView` branch) reuses `components/sales/detail/ServiceRow`/`serviceShapes.tsx` — the same collapsible, per-category detail a sale's `SaleDetailModal` shows — instead of a flat "descripción + precio" table: `lineasPorCategoria` groups `editing.lines` by category and stuffs `iva`/`subtotal` onto each line's `detalle` (those live on the quote line, not inside the form object `ServiceRow` expects). An early version only showed each line's short summary; don't go back to that. The same `cotizando` flag also hides "Proveedor" and "Método de Pago Proveedor" wherever a service shows them — procurement decisions that don't matter until the service is actually bought. `FinancialSection` (`forms/VoucherField.tsx`, shared by 11 of the 15 categories) takes `cotizando` and hides those two fields itself; the 4 forms with their own inline financial block (`TicketForm`, `HotelForm`, `InsuranceForm`, `PlanForm`) wrap them the same way, right where they already lived. "Costo Proveedor"/"Ganancia" stay visible either way — those ARE needed to quote a price.

**A quoted service can carry up to 5 photos — exclusive to quoting, a real sale never shows this field** (spec 021). `ImagesField` (`forms/VoucherField.tsx`, next to `FinancialSection`) is the one component all 15 `forms/*.tsx` use, each wrapped in `{cotizando && (...)}` — the only field in the whole `cotizando` pattern that shows *when* cotizando instead of hiding; everything else in that pattern does the opposite. It needs a `quoteId`/`lineId` pair to know where to upload: a brand-new, unsaved product has no `lineId` yet (the server only assigns one once the quote is saved), so the field shows "Guardá la cotización primero" instead of an upload button until then — same limitation `NewSaleWizard.tsx` already has with product vouchers, for the same reason (a file can't travel inside the quote's JSON before the row it belongs to exists). `Quotes.tsx::openEdit` carries each saved line's id into its product object as `lineId` (`{ ...linea.detalle, lineId: linea.id }`); `handleSave` strips it back out before POSTing, since it's screen bookkeeping, not a service field — if it rode along into `detalle`, it would go stale the moment the quote is saved again (every save replaces every line's id). `ProductFormsModal.tsx` is the relay: it takes `quoteId` from `Quotes.tsx` and reads `lineId` off whichever item is active per category. Uploading and deleting call the API directly and immediately (`api.uploadQuoteLineImage`/`deleteQuoteLineImage`) — they don't wait for the form's own "Guardar," the same way a product voucher doesn't. The read-only view (`ServiceRow.tsx`) shows the same images generically for all 15 categories — a sale's `item.images` is simply never set, so that block never renders there.

`src/utils/datosPersona.ts` is a hand-written mirror of `backend/src/utils/datosPersona.js` (rules in `backend/CLAUDE.md`): change both together; `pnpm test:reglas-espejo` in `backend/` fails if they drift.
