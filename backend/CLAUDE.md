## Domain conventions

- **Person data is validated in one place per side.** Names, document number by document type (CC/TI/CE/NIT numeric, PA alphanumeric; an NIT is valid by its 9–10 digit base, and the check digit after it — with or without hyphen — is optional and not verified), phone and birth date follow `backend/src/utils/datosPersona.js` (authoritative; `schemas/clients.schema.js` applies it and the controller passes `req.validatedBody`, already normalized) and are mirrored by hand in `frontend/src/utils/datosPersona.ts` — change both together (`pnpm test:reglas-espejo` fails if they drift). A 422 carries `error.details: [{ field, message }]` and the modal paints each one next to its input, so hooks must rethrow the original error, never wrap it in `new Error(msg)` (spec 003). The document type travels as **`docTypeId`** (the `tipos_documento.id` the screen picked from the DB list) for users, commissioners and responsables: `utils/tipoDocumento.js` resolves it to the abbreviation that selects the rule, and `docType` (abbreviation, or name) is still accepted for clients and older callers; the shared person fields live in `schemas/personaCampos.js`. Controllers must pass `req.validatedBody`, and a field the schema doesn't declare is dropped by Zod — add it to the schema when the service reads it.
- **A sale is created whole, and written in batches.** `services/ventaProductos.js` builds every row in memory (ids are generated up front) and writes ONE `createMany` per table, so the round trips to the pooler don't grow with the sale (spec 010 T5: a 3-ticket group sale went from ~40 s to ~4 s) — never go back to a `create` per row inside `createSale`. The wizard builds the draft in the browser (`localStorage`, keyed by empresa and user) and `POST /sales` writes the sale and all its products in one `transaccion`; each product list (`ticketData`, `hotelData`…) is validated per item by `schemas/products.schema.js` (422 names the field, e.g. `hotelData.0.hotelType`). There is no adding, editing or deleting products of an existing sale — those endpoints were unused and were removed (spec 002, T8). Files never travel in the sale JSON: the 201 returns `products: [{ category, index, detalleId }]`, and the browser then uploads each voucher with `PUT /sales/:saleId/products/:detalleId/voucher` (multipart `file`). Unknown `/api` routes answer 404 `ROUTE_NOT_FOUND` in the API format.
- **VAT is on the TA, never inside it.** `iva`/`iva_total` (`detalle_venta`/`ventas`) are separate columns, derived server-side from `ta` at a fixed 19% (`saleTotals.js`: `TASA_IVA`, `calcularIva`, `datosFinancieros`) — the client never sends `iva`. Commission and "Ganancia Oficina" are computed on net TA, never TA+IVA (spec 005).
- **Flights and the sales list use Bogotá days, and flight direction is inferred.** `dateFrom`/`dateTo` on `/flights`, `/flights/checkins` and `/sales` are `YYYY-MM-DD` days in Bogotá, both inclusive (`rangoDeDias` in `utils/fechas.js` → `[desde, hasta)`); `GET /sales` validates every filter (`listSalesQuerySchema`: search ≤ 100, status enum, ids, sort whitelist, from ≤ to) and answers 422 with the field (spec 016); the browser sends the month as two strings, never `toISOString()`. Ida/regreso is not stored: in a `round_trip` the legs are cut at the largest gap between arrival and next departure. Ticket airports and baggage plans (`"<aerolínea> - <tarifa>"` or id) are validated before the transaction in `sales.service.js` (`_validarTiquetes`) — unknown → 422 with the field, there is no `UNK` airport. `recalcularProducto` locks the product row (`FOR UPDATE`). Plan flights are cancelled per direction (`canceled_at_ida`/`_regreso`, `reason_canceled_*` on `prod_planes`) (spec 004; `docs/designs/vuelos-fechas-de-bogota-y-direccion.md`).
- The 15 product categories (`ticket`, `hotel`, `insurance`, `plan`, `checkin`, `migration`, `simcard`, `car`, `finca`, `tour`, `convention`, `restaurant`, `visa`, `passport`, `pet`) have one name across URL segments, `detalle_venta.categoria` and `catalog/products.js`; adding one means the catalog and the enum, not new strings scattered around.
- **The voucher is built server-side** (spec 011): `services/voucher/plantilla.js` turns a sale (the same `getSaleById` + `getSaleProducts` the detail screen reads) and the agency profile into a `pdfmake` document; each product category is one entry of `SECCIONES`. `services/voucher/index.js` caches it in the `vouchers` bucket under a content hash (bump `PLANTILLA_VERSION` when the layout changes), returns 5-minute signed URLs, and writes `vouchers_venta` only after the email actually went out. The browser never builds or uploads a PDF.
- **Any service can hang inside a package** (spec 015): the wizard lets a service be linked to a package of the same sale (`parentDetalleId`), and `META[slug].canBeChild` says which categories the read path attaches under `includedProducts[slug]` of the `planData` item (every category except `plan`). A child is not in its top-level section. The voucher prints children under their package through `bloquesDeHijos`; keep the two lists in step when adding a category.
- **Seats and reservation are per passenger** (spec 012): `pasajeros_detalle.asientos` is JSON `[{ tramo, asiento }]`, where `tramo` is the leg's `orden` in its ticket (legs, outbound stops, return leg, return stops — the order `ventaProductos.js` writes). The titular's `nroReserva` is required; other passengers and `prod_tiqueteria.nro_reserva` inherit it. `tramos_vuelo.asiento` and `pasajeros_detalle.asiento` are legacy, read only as a fallback.
- **Client preferred destinations are free text, up to 5** (spec 017): `cliente_destinos` (`orden` 1–5, oldest first) plus the copy `clientes.destino_reciente` (the highest `orden`), both written only by `escribirDestinos` in `clients.service.js` in one `transaccion` — never write one without the other. `utils/destinos.js` (`normalizarDestinos`) is the rule (trim, 2–60 chars, case-insensitive duplicates keep their last occurrence, max 5); `escribirDestinos` also reuses the agency's existing spelling of a destination (oldest row, case-insensitive), so "pEreira" is stored as "Pereira", used by `clients.schema.js` for the 422 (`destinations` / `destinations.<i>`). `PUT /clients/:id` with `destinations` replaces the list; without it, leaves it. `GET /clients?destination=` filters by `destino_reciente`, `&destinationAll=true` by any (`cliente_destinos: { some }`), same `where` for rows and count. `GET /clients/destinations?search=` suggests up to 10 agency-wide destinations with no per-advisor scope (only destination names, never clients).
- **A quote reuses a sale's validation, relaxed; a sale stays strict** (spec 007): `quotes.schema.js`/`quotes.service.js` share `schemas/productArrays.js` and `services/productValidation.js` with `sales.schema.js`/`sales.service.js`, but call them with `{ relajado: true }` / `{ exigirReserva: false }` — a quote requires nothing (no client, no `supplierCost`, no ticket titular `nroReserva`); `sales.schema.js`/`sales.service.js` never pass those options, so a sale is validated exactly as before. What IS sent is still checked the same in both (an unknown airport or `hotelType` is rejected either way) — only *requiredness* was relaxed, not correctness. `detalle_cotizacion.detalle` (`Json?`) stores the same per-category object a sale uses (`TicketData`, `HotelData`...); `convertToSale` returns it grouped by category to prefill the sale wizard, where the normal strict validation applies once the sale is actually submitted. `cotizaciones.nombre` is a free, optional label ("Cartagena plan para 2") to tell quotes apart in the list — same looseness as `fechaVencimiento`/`observaciones`, nothing required.
- **The PDF of a quote and the voucher of a sale describe each product category from one shared module, never two** (spec 007/011): `services/voucher/secciones.js` holds `SECCIONES` (the title + label/value pairs per category), `bloqueTiquete` (flight itinerary with legs, passengers, seats) and the `rejilla`/`tarjeta`/`titulo` layout helpers; both `services/voucher/plantilla.js` and `services/quotes/plantilla.js` import from it instead of keeping their own copy of "which field shows under which label" — the exact drift spec 015 already warned about for `includedProducts`. A quote's PDF renders a full per-category block per line (same fields a sale's voucher shows) ahead of its own price table, using `detalle_cotizacion.detalle` directly; a field a quote never asked for (reservation number, confirmation number) is simply empty and `rejilla` already hides empty pairs, so nothing extra had to be done to keep supplier cost/profit/payment-method out of it — no section ever included those. Adding a category still means touching `SECCIONES` once, for both documents.
