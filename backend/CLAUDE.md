## Domain conventions

- **Person data is validated in one place per side.** Names, document number by document type (CC/TI/CE/NIT numeric, PA alphanumeric; an NIT with an unambiguous check digit — hyphen or 11 digits — must have the right one, DIAN mod 11), phone and birth date follow `backend/src/utils/datosPersona.js` (authoritative; `schemas/clients.schema.js` applies it and the controller passes `req.validatedBody`, already normalized) and are mirrored by hand in `frontend/src/utils/datosPersona.ts` — change both together (`pnpm test:reglas-espejo` fails if they drift). A 422 carries `error.details: [{ field, message }]` and the modal paints each one next to its input, so hooks must rethrow the original error, never wrap it in `new Error(msg)` (spec 003). The document type travels as **`docTypeId`** (the `tipos_documento.id` the screen picked from the DB list) for users, commissioners and responsables: `utils/tipoDocumento.js` resolves it to the abbreviation that selects the rule, and `docType` (abbreviation, or name) is still accepted for clients and older callers; the shared person fields live in `schemas/personaCampos.js`. Controllers must pass `req.validatedBody`, and a field the schema doesn't declare is dropped by Zod — add it to the schema when the service reads it.
- **A sale is created whole, and written in batches.** `services/ventaProductos.js` builds every row in memory (ids are generated up front) and writes ONE `createMany` per table, so the round trips to the pooler don't grow with the sale (spec 010 T5: a 3-ticket group sale went from ~40 s to ~4 s) — never go back to a `create` per row inside `createSale`. The wizard builds the draft in the browser (`localStorage`, keyed by empresa and user) and `POST /sales` writes the sale and all its products in one `transaccion`; each product list (`ticketData`, `hotelData`…) is validated per item by `schemas/products.schema.js` (422 names the field, e.g. `hotelData.0.hotelType`). There is no adding, editing or deleting products of an existing sale — those endpoints were unused and were removed (spec 002, T8). Files never travel in the sale JSON: the 201 returns `products: [{ category, index, detalleId }]`, and the browser then uploads each voucher with `PUT /sales/:saleId/products/:detalleId/voucher` (multipart `file`). Unknown `/api` routes answer 404 `ROUTE_NOT_FOUND` in the API format.
- **VAT is on the TA, never inside it.** `iva`/`iva_total` (`detalle_venta`/`ventas`) are separate columns, derived server-side from `ta` at a fixed 19% (`saleTotals.js`: `TASA_IVA`, `calcularIva`, `datosFinancieros`) — the client never sends `iva`. Commission and "Ganancia Oficina" are computed on net TA, never TA+IVA (spec 005).
- **Flights use Bogotá days, and direction is inferred.** `dateFrom`/`dateTo` on `/flights` and `/flights/checkins` are `YYYY-MM-DD` days in Bogotá, both inclusive (`rangoDeDias` → `[desde, hasta)`); the browser sends the month as two strings, never `toISOString()`. Ida/regreso is not stored: in a `round_trip` the legs are cut at the largest gap between arrival and next departure. Ticket airports and baggage plans (`"<aerolínea> - <tarifa>"` or id) are validated before the transaction in `sales.service.js` (`_validarTiquetes`) — unknown → 422 with the field, there is no `UNK` airport. `recalcularProducto` locks the product row (`FOR UPDATE`). Plan flights are cancelled per direction (`canceled_at_ida`/`_regreso`, `reason_canceled_*` on `prod_planes`) (spec 004; `docs/designs/vuelos-fechas-de-bogota-y-direccion.md`).
- The 15 product categories (`ticket`, `hotel`, `insurance`, `plan`, `checkin`, `migration`, `simcard`, `car`, `finca`, `tour`, `convention`, `restaurant`, `visa`, `passport`, `pet`) have one name across URL segments, `detalle_venta.categoria` and `catalog/products.js`; adding one means the catalog and the enum, not new strings scattered around.
- **The voucher is built server-side** (spec 011): `services/voucher/plantilla.js` turns a sale (the same `getSaleById` + `getSaleProducts` the detail screen reads) and the agency profile into a `pdfmake` document; each product category is one entry of `SECCIONES`. `services/voucher/index.js` caches it in the `vouchers` bucket under a content hash (bump `PLANTILLA_VERSION` when the layout changes), returns 5-minute signed URLs, and writes `vouchers_venta` only after the email actually went out. The browser never builds or uploads a PDF.
